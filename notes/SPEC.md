# Tillkite spec

Tillkite is a small, fast PHP router that maps URLs to PHP files.

This document is the design spec.

## Goals

- A small, fast router for PHP 8.4 and later, with no runtime dependencies.
- Two ways to use it: install it with Composer, or `require` a single generated `tillkite.php` file.
- Runs unchanged under `php -S` (development) and php-fpm (production).
- A matched request costs two `stat`s, one OPcache'd include for the route cache, one hash lookup or one regex, and then the handler include.
- Behavior you can predict by reading the routes file.
- A small public API, with each part chosen deliberately, because public APIs are hard to change later.

**Out of scope:** routing from the filesystem layout, closures as handlers, middleware stacks, request and response objects, named routes and URL generation, command-line commands, and automatic `OPTIONS` responses.

- **Package:** `.gitattributes` marks the development files `export-ignore`, so what Composer installs from a release, and GitHub's archives, hold only `src/`, `dist/tillkite.php`, `bin/tillkite`, `composer.json`, `README.md`, `CHANGELOG.md` and `LICENSE`. Benchmarks, tests and the example come from a clone.
- **Scripts on the web:** a checkout can end up under a document root, so `bin/dist.php`, `bin/tillkite`, `bench/run.php` and `bench/load.php` answer anything but the command line with a 404 before they load or do anything. A web request to `bench/load.php` would otherwise start nginx and php-fpm and leave them running, and one to `bin/dist.php` would rewrite `dist/tillkite.php`. `bench/load-front.php` has to run under php-fpm, so it answers a 404 when `BENCH_DIR` is empty, which only the nginx configuration `make load` writes sets.
- **Makefile:** all project jobs run through `make`, never Composer scripts. Targets: `help`, `all` (autoload, style, lint, analyze, tests), `autoload` (runs `composer dump-autoload`, needed after adding or removing a class, because the classmap is authoritative), `style`, `lint`, `analyze`, `tests` (builds `dist/tillkite.php` first, then runs the suite against `src/` and against it), `dist`, `serve` (runs `php -S` on the example site, at http://localhost:8417), `serve-dist` (the same on `dist/tillkite.php`, loaded with `auto_prepend_file`, at http://localhost:8418, so both can run side by side) and `bench`. Five more run in Docker (see the next bullet): `load`, `fpm`, `apache`, `root` and `matrix`.
- **Docker:** a developer installs only PHP 8.4 or later and Composer, and `composer install` checks PHP's extensions. Everything else runs on the host, because the tests take about a second there, and editors run PHPStan and php-cs-fixer with the local PHP. The targets that need more run in Docker, so they need nothing else installed:
  - `make load` needs nginx, php-fpm and oha. It runs `bench/load.php` on PHP 8.5, or the version `PHP=` names.
  - `make fpm` runs `tests/fpm-tests.php` under nginx and php-fpm, against `src/` and against `dist/tillkite.php`, on PHP 8.5, or the version `PHP=` names. It sets `TILLKITE_FPM=1`, without which those tests are skipped.
  - `make apache` runs `tests/apache-tests.php` under Apache with mod_php, against `src/` and against `dist/tillkite.php`, on PHP 8.5, or the version `PHP=` names, behind `tests/fixtures/fpm/public/.htaccess`, which a test checks is the README's. It sets `TILLKITE_APACHE=1`, without which those tests are skipped. It's the setup many hosts have, where `getenv()` reads Apache's table of the request's variables, not FastCGI's. Apache runs in a session of its own, since it stops by signalling its process group.
  - `make root` runs `tests/cache-tests.php` as root, against `src/` and against `dist/tillkite.php`, on PHP 8.5, or the version `PHP=` names, for its test that the cache won't use a directory that belongs to another user, which takes `chown()`. Everything else runs as `dev`, so that test is skipped there. `docker/run.sh` gives `vendor/` back to `dev` after Composer runs as root.
  - `make matrix` runs `docker/check.sh` on PHP 8.4 and 8.5, the versions CI uses: lint, analyze and tests, with `TILLKITE_FPM=1`, so the php-fpm tests run too, and then checks that the `dist/tillkite.php` and `src/app.php` that the tests built match yours. It catches a problem with the PHP version you don't have, and with Linux's case-sensitive file names, before CI does. Then it runs `make root`'s tests for that version.
  - `docker/Dockerfile` builds `tillkite-apache:VERSION`, its `apache` stage, from PHP's official `php:VERSION-apache` image, with Composer, for `make apache`, and `tillkite-dev:VERSION`, its last stage, from PHP's official `php:VERSION-fpm` image, which has the CLI and OPcache too. It adds Debian's nginx, oha from its GitHub release, pinned and checked against its SHA-256 (Debian doesn't package it), and Composer, pinned. Everything runs as a user named `dev`, because php-fpm won't run as root unless it's told to.
  - `docker/run.sh` copies the repository, mounted read-only, into the container, leaving out `.git`, `vendor/` and the example's route cache, so nothing in your checkout changes. Then it runs `composer install`, with your `composer.lock` when there is one, and the command. `vendor/` is a Docker volume for each PHP version, `tillkite-vendor-VERSION`, so after the first run there's nothing to install. Working in a copy also keeps the load test's requests off the files shared from the host, which are slow to check on macOS.
- **composer.json:** package `josephscott/tillkite`, type `library`, `"php": ">=8.4"`, classmap autoload of `src/`, and `bin/tillkite` as its command, which Composer links as `vendor/bin/tillkite`. Development dependencies are pinned to exact versions: `josephscott/phpcsfixer-config`, `phpstan/phpstan`, `pestphp/pest`, plus `nikic/fast-route`, `symfony/routing` and `wilaak/radix-router` for benchmarks.
- **dist/tillkite.php:** `make dist` runs `bin/dist.php`, which combines every class in `src/` into one file under one `namespace Tillkite;`. Its header has the version, from `App::VERSION`, and the MIT license, because the file is often copied on its own. Every class file must start with the same `<?php`, `declare` and `namespace` lines, and the build stops if one doesn't. It's committed so projects without Composer can download it straight from the repo. It ends with a check that runs `Tillkite\Starter` when the file is run as a command, like `php tillkite.php new my-site` (see [Making a site](#making-a-site)). It also writes `App::SOURCE_HASH` into `src/app.php` (see [Route cache](#route-cache)). CI runs `make dist` and fails if the result differs from the committed files. php-cs-fixer skips it, since it's built from files that are already fixed.
- **example/:** a complete site that uses `Tillkite\App` directly, so it's simple to copy, and every feature: static and dynamic routes, nested optional parts, catch-all routes, multiple methods per route, `'*'` routes, the app's before-file, a group of routes whose before-file runs after it, stops the handler with `error()` and hides which paths under its prefix exist, a group that runs only its own before-file with `before_only` and has its own JSON 404 and 405 files, and a route with no before-files, a webhook that checks the request's signature itself, with `hash_equals()` and a secret from the environment, the 403, 404, 405 and 500 files, handlers, before-files and error files in directories inside `handlers/` (`users/`, `admin/`, `api/`, `hooks/` and `errors/`), a handler that shows the 404 page with `error()`, an unbuffered streaming route, the route cache, the timing header, only in development (each page's footer shows it and explains each step), `file()` (the docs pages are files in `docs/` that the catch-all route names), `trailing_slash` set explicitly, trailing-slash redirects, `route()` (each page shows the route that matched), `group()` (the nav marks the admin pages) and `template()` (each handler prints its own `<main>` between the header and the footer, which are templates, and runs the route part under its heading, and the header runs the head and the nav as templates of their own), `register()` and `get()` (`index.php` registers the blog's posts, which its handler gets), and `Tillkite\Escape` (the handlers and templates escape text with `Esc::html()`). Under `php -S`, each page also has a stack trace, hidden until it's opened. It's both a demo and the end-to-end test fixture.
- **CHANGELOG.md:** follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Every change adds a line under `Unreleased` in the same commit, and a release moves those lines under its version number and sets that number in `App::VERSION`, which is part of the route cache's key.
- **CI:** GitHub Actions on PHP 8.4 and 8.5 runs lint, analyze, tests and the `dist` check, then `make fpm`, `make apache` and `make root` for that version. Its token can only read the repository, and the checkout doesn't keep it. `make matrix` runs the same checks locally, but not the Apache tests.

## Code style

All code follows the rules in [josephscott/phpcsfixer-config](https://github.com/josephscott/phpcsfixer-config) and the simple-return guidance in [Code opinion: simple return statements](https://josephscott.org/blog/2024/08/code-opinion-simple-return-statements/):

- `declare( strict_types = 1 );` in every file.
- Tabs, spaces inside parentheses, opening braces on the same line, return types written `function name() : type`.
- snake_case for methods, properties and variables. Options are public typed properties.
- Simple return statements: assign to a variable, then return the variable. No nested ternaries. Use an `if` that returns `true`, then `return false`, instead of returning a boolean expression.
- Strict comparisons, `! $x`, single quotes, `$i++`, short arrays with trailing commas in multi-line arrays, `//` comments.
- No exceptions: Tillkite never throws and never catches. Failures are reported through return values (see [Errors](#errors)). The one `try` is in `template()`, a `try`/`finally` that catches nothing (see [Templates](#templates)).
- No `extract()`. A file gets its values in one array with a name, like `$params` or `$data`, so it's always clear where a value came from.
- In namespaced code, PHP's own functions and constants have a leading `\`, like `\strlen()` and `\PHP_SAPI`. Without it, PHP looks in the namespace first on every request, can't compile calls like `\strlen()` and `\count()` to faster opcodes, and works out class constants like `\E_ERROR | \E_PARSE` on every request instead of once (see [Under load](#under-load)). php-cs-fixer adds them; the shared config leaves this rule off, so `.php-cs-fixer.dist.php` turns it on. The tests and the example site are in the global namespace, where it makes no difference.
- No `@` error suppression. When a PHP function reports failure with a warning, a temporary `set_error_handler()` takes the warning and `restore_error_handler()` follows right after. Unlike `@`, this keeps the warning away from the app's own error handler.
- PHPStan for static analysis and Pest for tests.

## Using Tillkite

```php
<?php // public/index.php
declare( strict_types = 1 );

require __DIR__ . '/../vendor/autoload.php'; // or: require __DIR__ . '/../tillkite.php';

$tillkite = new Tillkite\App( [
	'routes' => __DIR__ . '/../routes.php',
	'handlers' => __DIR__ . '/../handlers',
	'templates' => __DIR__ . '/../templates',
	'cache' => __DIR__ . '/../var',
] );
$tillkite->server_timing = true;

return $tillkite->run();
```

```php
<?php // routes.php
declare( strict_types = 1 );

return [
	[ 'GET', '/', 'home.php' ],
	[ 'GET', '/users/new', 'users/new.php' ],
	[ 'GET', '/users/{id:\d+}', 'users/show.php' ],
	[ [ 'GET', 'POST' ], '/contact', 'contact.php' ],
	[ 'GET', '/blog[/{page:\d+}]', 'blog.php' ],
	[ 'GET', '/docs/{path:.+}', 'docs.php' ],
	[ 'GET', '/export.csv', 'export.php', [ 'buffer' => false ] ],
	[ 'POST', '/hooks/github', 'github.php', [ 'before' => false ] ],
	[ '*', '/webhook', 'webhook.php' ],
	[ 'prefix' => '/admin', 'before' => 'admin-before.php', 'routes' => [
		[ 'GET', '', 'admin/dashboard.php' ],
		[ 'GET', '/{page}', 'admin/page.php' ],
	] ],
];
```

- Development: `php -S localhost:8000 -t public public/index.php`
- Production: nginx sends every request that isn't a real file, or is for a PHP file, to the same `index.php`. Without the middle block, nginx would send the source of any other PHP file in `public/`, which `php -S` doesn't run either (see [php -S and php-fpm](#php--s-and-php-fpm)). The README has the same rules for Apache, as a `.htaccess` file:

```nginx
location / {
    try_files $uri /index.php$is_args$args;
}
location ~* \.php$ {
    rewrite ^ /index.php last;
}
location = /index.php {
    include fastcgi.conf;
    fastcgi_pass unix:/run/php/php-fpm.sock;
}
```

### Making a site

`vendor/bin/tillkite new [directory]` with Composer, or `php tillkite.php new [directory]` with the dist file, makes a site to start from, in the directory or the current one. Both run `Tillkite\Starter::main()`, an internal class. The site has:

- `init.php`, which everything starts from: `public/index.php`, and any script the developer adds, with `require __DIR__ . '/../init.php';`. It's the place for what the web and scripts both need, like a database connection. Its comment shows one in `$db`, which `public/index.php` gets when it requires `init.php`. The app isn't in it, because routing is only for the web, and with the dist file, neither is Tillkite, which `public/index.php` requires. With Composer, it requires the autoloader, since scripts need the site's other packages too, by its path from the site's directory, so the site still works when it moves along with `vendor/`.
- `public/index.php`, which starts with the settings for production (see [PHP's error settings](#phps-error-settings)), then requires `init.php`, and with the dist file, `lib/tillkite.php`, a copy of the file that made it. Then it creates the app with `routes`, `handlers`, `templates`, `cache`, `before` and the 404, 405 and 500 `errors`, and returns `$tillkite->run()`. Its comment shows registering `$db` with the app (see [Sharing values](#sharing-values)).
- `public/style.css`, a few lines that use system fonts and the browser's own light and dark colours.
- `routes.php`, with `/` and `/hello/{name}`.
- `templates/header.php` and `templates/footer.php`, the top of the page, up to `<body>`, and the bottom, which each handler runs with `template()` before and after its content. The header takes the page's title, for `<title>`, and each page prints its own `<main>` and `<h1>`, so a page can have a different shape, or run other templates in their place, without a layout that every page has to fit. The header escapes the title with `Esc::html()`, as `hello.php` does for its parameter and the 404, 405 and 500 files for what they show, with `use Tillkite\Escape as Esc;` at the top. Its icon is an empty data URL, so browsers don't ask for `/favicon.ico`, which would run the 404 page.
- `handlers/`: `home.php`, `hello.php`, the 404, 405 and 500 files, and `before.php`, which sends `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and `Content-Security-Policy: frame-ancestors 'none'`. Misses run it too, so the error pages get them. The 500 file shows `$error` under `php -S` and sends it to the error log anywhere else, because Tillkite doesn't log an exception that a 500 file handles.
- `var/.gitignore`, which ignores everything in `var/` but itself, so the cache directory is in the site's repository and the cache isn't.

It leaves `server_timing` off and `trailing_slash` at its default. It never overwrites a file or writes through a symlink: if any file it would make is there, or a symlink, even to nothing, is in place of one of them or of a directory it would put them in, it lists them on stderr, writes nothing and exits with 1. It creates each file with `fopen()`'s mode `x`, so a file or symlink that appears after that check stops it instead of being written over or through. A dist file that's already the site's `lib/tillkite.php` doesn't count itself, and isn't copied. Then it lists the files it made and prints the `php -S` command and an nginx `server` block with the site's `public/` as its root, in quotes, so a space, `;`, `{` or `#` in the path stays part of it. nginx has no escape for `$`, which starts a variable, and a path with one, or with a control character, gets `/path/to/public` and a comment that says why instead. A file it can't write stops it with PHP's warning as the message.

## Public API

The public API is two classes, `Tillkite\App`, with a constructor, public option properties and ten methods, and `Tillkite\Escape`, with seven static methods (see [Escaping](#escaping)), and the `new` command (see [Making a site](#making-a-site)). Everything else is internal. `App::REASONS`, the status codes `errors` takes, is public only so the compiler can check `errors` against it.

### Constructor and options

`new Tillkite\App( array $options = [] )` sets the public property with the same name for each key. An unknown key, a value of the wrong type, or setting a property that doesn't exist (caught by `__set()`), is recorded as a configuration problem and reported by `run()` (see [Configuration problems](#configuration-problems)). The constructor takes only the options below; a subclass sets its own properties directly.

| Property | What it does | Default |
|---|---|---|
| `routes` | Path to a PHP file that returns the routes array | Required |
| `handlers` | Directory that every handler, before-file and error file path is relative to | Directory containing the routes file |
| `cache` | Directory for the compiled route cache | Not set: routes are compiled on every request |
| `templates` | Directory that `template()` names are relative to | The handlers directory |
| `base` | URL prefix the app is mounted under, e.g. `/app`. It starts with `/` and doesn't end with one. | None |
| `trailing_slash` | `false`: URLs never end in `/`. `true`: they always do. | `false` |
| `buffer` | Buffers output from before-files, handlers and error files. Set it to `false` to turn buffering off for the whole app. A route can override it either way with `[ 'buffer' => true ]` or `[ 'buffer' => false ]`. | `true` |
| `server_timing` | Send the router's `Server-Timing` header | `false` |
| `before` | File that runs before every handler, and before the response when no route matches. A route can add its own to run after it, run only its own, or run none (see [Running files](#running-files)). | None |
| `errors` | Files to run for error responses, e.g. `[ 404 => '404.php', 405 => '405.php', 500 => '500.php' ]`. It takes 500 and the standard 4xx codes. Tillkite sends 404, 405 and 500 itself, and any 4xx file but 405 runs for `error()`. | Plain-text responses, like `404 Not Found`. With no 500 file, an uncaught exception is a fatal error (see [Fatal errors](#fatal-errors)). |
| `methods` | Custom HTTP methods to allow in addition to the standard ones, e.g. `[ 'PURGE' ]` | None |

`routes`, `handlers`, `cache` and `templates` must be absolute paths. Build them from `__DIR__`. A relative path would resolve against the current working directory, which differs between `php -S` and php-fpm, so a relative path is a configuration problem.

### Methods

- **`run() : bool`** handles the web request. It returns `false` only under `php -S`, for a request that should be served as a static file. `index.php` returns this value.
- **`route() : ?array`** returns the matched route as written in the routes file, with its group's prefix joined to its pattern, or `null` if nothing matched.
- **`group() : ?string`** returns the prefix of the matched route's group as written, like `'/admin'`, or `null` if it isn't in one. When no route matched, it's the prefix of the group the path is under (see [Groups](#groups)).
- **`uri() : string`** returns the request's URI as the web server sent it, with its query string and before `base` is taken off, and **`method() : string`** returns its method. They're `$_SERVER['REQUEST_URI']` and `$_SERVER['REQUEST_METHOD']`, read the way `run()` reads them, so a page that shows them doesn't make PHP build `$_SERVER` (see [Why Tillkite's code never names $_SERVER](#why-tillkites-code-never-names-_server)). Each reads its value once, the first time it or `run()` needs it.
- **`timings() : array`** returns the milliseconds for each step that ran (see [Timing](#timing)).
- **`error( int $code ) : false`** shows the error page for a 4xx code other than 405, from a before-file or handler (see [error()](#error)).
- **`template( string $template, array $data = [] ) : string`** runs a template and returns what it printed (see [Templates](#templates)).
- **`register( string $name, mixed $value ) : void`** makes a value available to before-files, handlers, error files and templates (see [Sharing values](#sharing-values)).
- **`get( string $name ) : mixed`** returns the value registered as `$name`, or `null`, which it logs, when there's none.
- **`file( string $directory, string $name ) : ?string`** returns the real path of the file named `$name` inside `$directory`, or `null` when there's none (see [Files named by a request](#files-named-by-a-request)).

### Inside before-files, handlers and error files

- `$params` holds the route parameters. When no route matches, it holds the parameters of the group's prefix, or nothing.
- `$tillkite` is the `App` object (or your subclass of it), whose `get()` returns what was registered with it.
- The 500 file also gets `$error`: the uncaught exception, thrown by the app's own code or by PHP itself, or, for a 500 that isn't an exception, a `RuntimeException` that Tillkite creates to describe it. Tillkite never throws it.

### Inside templates

- `$data` is the array passed to `template()`, or `[]`.
- `$tillkite` is the `App` object, so a template can run other templates, and get what was registered.

### Helper methods

A site that needs no helpers uses `App` directly. Add helpers by extending the class:

```php
class My_App extends Tillkite\App {
	public function json( mixed $value ) : void {
		header( 'Content-Type: application/json' );
		echo json_encode( $value );
	}
}
```

Handlers then call `$tillkite->json( ... )`. `App` is not `final`, but everything internal to it is `private`. The internal classes are `final` and marked `@internal`, so they can change without breaking anyone.

## Routes

Each route is `[ method, pattern, file ]`, with an optional fourth element for route options.

- **Method:** one string, a list of strings, or `'*'` for any method. Methods must be uppercase. Allowed methods are the standard ones (`GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `CONNECT`, `TRACE`) plus anything in the `methods` option. A `GET` route also answers `HEAD`.
- **File:** relative to `handlers`.
- **Route options:** `buffer` (`true` or `false`), `before` (a file that runs after the app's before-file, or `false` to run no before-files) and `before_only` (a file that runs in place of the app's before-file). A route sets at most one of `before` and `before_only`.

### Groups

A group is `[ 'prefix' => '/admin', 'routes' => [ ... ] ]`, with optional `before`, `before_only` and `buffer` keys that work as a route's options do, and an optional `errors` key. Keys tell a group from a route, which is a list.

- **Prefix:** starts with `/` and doesn't end with one. It can have parameters, but not optional parts, which have to be at the end of a pattern.
- **Patterns:** each route's pattern is joined to the prefix, so it starts with `/` or `[`, or is `''` for the prefix by itself.
- **Before-files:** the group's options apply to the app's before-file, and then the route's options apply to the result (see [Running files](#running-files)). So a route in a group runs at most three: the app's, the group's and its own.
- **Buffer:** a route's own `buffer` wins over its group's, which wins over the app's.
- **Error files:** `errors` takes the same codes and files as the app's option, and they take the place of the app's for the codes it lists, so an API group can have JSON error pages. They run for the group's routes, for `error()` and for exceptions in their files, and for the misses under its prefix.
- **Misses:** a path under the group's prefix, which is the prefix, or the prefix and a `/` and more, that no route matches runs what a route in the group with no options of its own would: its before-files, and then its error files (see [When no route matches](#when-no-route-matches)). When the path is under more than one group's prefix, the prefix with the most segments counts, and the first in the list of those with as many, so a broader group listed first, like `/api` before `/api/admin`, can't take the misses of a narrower group's login check. The compiler orders the regex's alternatives that way, so it costs nothing at request time. The compiler builds one regex from every group's prefix, with a MARK for each group and the prefix's parameters as its matches, and `Matcher` runs it only after a miss. It's left out only when there are no groups. If the regex fails, as at the backtrack limit, the miss is a 500, so a group's before-files are never skipped.
- **`group()`:** returns the group's prefix as written, for its routes and for the misses under its prefix, so a page can tell which section it's in without checking the pattern. Each route in a group has its group's key in the compiled routes, where the group keeps its prefix and error files, so a route in a group has an entry in the files table even when it runs only the app's before-file.
- **Order:** the group's routes take its place in the list. Compiling expands each group into ordinary routes before anything else, so matching, the checks for routes that can never match, the cache and `route()` all see full patterns.
- **One level:** a group inside a group is a compile error. See [Why groups are one level deep](#why-groups-are-one-level-deep).
- **Numbering:** a compile error names a route in a group by both positions, like route 4.2, the second route in the group that's fourth in the routes file. A group with problems is reported as `Group 4`, and its routes aren't checked until it's fixed, so they don't each repeat its problem.

### Patterns

- Literal segments must match exactly, and case matters. Every pattern starts with `/`.
- `{name}` matches one path segment.
- `{name:regex}` uses your own regex. It can't contain capturing groups; use `(?:...)` instead. It can't use a backtracking verb such as `(*ACCEPT)` or `(*MARK)` either.
- A catch-all is a regex that allows `/`, such as `{path:.+}`.
- Optional parts go in `[...]` at the end of a pattern and can be nested: `/blog[/{page}[/{sort}]]`. A missing optional parameter isn't set in `$params`.
- Non-ASCII characters in literal segments are percent-encoded when routes are compiled, with uppercase hex, so `/café` matches the `/caf%C3%A9` that browsers send.

## Matching

1. Take `REQUEST_URI` up to the `?`, then remove `base`. A request outside `base` is a 404. With `base` set, the root URL is `/app` or `/app/`, following `trailing_slash`, and the other form gets a 308.
2. Check routes top to bottom. The first match wins. Matching uses the raw, still-encoded path, and each captured parameter is then decoded with `rawurldecode`, so an encoded slash (`%2F`) can't create an extra segment. A value that was encoded then has to match its regex again, decoded, one with the default regex can't decode to a `/` or a `\`, and none can have a `..` segment or a null byte (see [Checking decoded values](#checking-decoded-values)).
3. If nothing matches, try these in order:
   - **405:** the path matches a route for another method. Respond 405 with an `Allow` header, then run the 405 file if one is set.
   - **308:** adding or removing the trailing slash gives a URL that matches a route. Redirect to it, keeping the query string. `Location` holds only the path (including `base`), never the `Host` header. A `Location` that would start with `//` or `/\` gets a 404 instead, because browsers read those as links to another site. The path and query come from the request, and a web server can pass on bytes that aren't printable ASCII, as nginx does for bytes from 0x80, so each of those is percent-encoded, and `Location` holds only what a URL can. That also means a tab, which browsers take out of a URL, can't turn `/<tab>/evil.example` into `//evil.example`. `php -S` drops such a request, so it's checked under php-fpm, not in the tests.
   - **404:** respond 404, then run the 404 file if one is set.

The step 3 checks only run when nothing matched, so a matched request never pays for them.

### Checking decoded values

A regex matches the value as it is in the URL, where `%2E` isn't a dot, and the handler gets it decoded. So under nginx and php-fpm, `{name:[^./]+}` let `/files/%2E%2E%2Fetc%2Fpasswd` through as `../etc/passwd`, and `{name:(?!admin$)[^/]+}` let `/u/%61dmin` through as `admin`. A regex that lists what's allowed, like `\d+` or `[a-z]+`, was never affected, since it doesn't take a `%`. So a parameter whose value changes when it's decoded has to match its regex again, on its own.

- **Which regexes:** `Compiler::checks()` makes one for each parameter with a regex of its own, for each route and group prefix, in `checks`. A regex that names `%` was written for the encoded form and wouldn't match the decoded value, so its check is `''`, for none.
- **The default regex:** `{name}` takes one segment, and `/files/..%2F..%2Fetc%2Fpasswd` used to give it `../../etc/passwd`, which a handler that builds a file path from it would follow out of its directory. Symfony's router decodes the path before it matches it, so its default never holds a slash. So a parameter with no entry in `checks`, which is one with the default regex, written out as `[^/]+` or not, is turned away when its decoded value has a `/`, or a `\`, which Windows reads as one. A raw `\`, which a browser sends as a `/` but nginx passes on, is turned away too, so `match()` decodes for a path with a `\` in it, as for one with a `%`. `Matcher::decoded()` looks for them with one `strpbrk()`, so the parameters most routes have need no regex in the cache. `..` by itself is still one segment, and passes. The compiler's check for a static route that an earlier dynamic route hides has the checks too, so `/files/a%2Fb` after `/files/{name}` is a route of its own, not one that never matches.
- **A value that fails:** the route doesn't match, and the response is a 404 under the group it's in, so the group's before-files still run. There's no 405 or 308, since those look for the same route. The routes after it aren't tried, unlike a value that fails its regex in the URL, because PCRE has already chosen between them, and trying them would take a regex for each route in the cache. A failed prefix is outside its group, as it would be if the value weren't encoded. When PCRE fails, it's a 500, as with any other regex.
- **What it can't see:** the check runs on the value alone, so a lookaround that looks at the text around the parameter, like `[a-z]+(?=-)`, fails it. That matters only for a value that was encoded.
- **`..` segments:** no parameter takes a value with a `..` segment, between `/` or `\` or at either end, whatever its regex: `/files/..`, `/files/%2E%2E`, and `/docs/a/../b` for `/docs/{path:.+}`, are 404s, like a value that fails its check. In a file path a `..` segment leaves the directory, and with a parameter for each of several segments, or a catch-all, it climbs as far as it likes, which is how a page that reads a file named by its path ends up sending `/etc/passwd`. A browser takes `..` segments out of a URL before it sends it, so only a request made by hand has one, and no site's own links stop working. `Matcher::decoded()` makes the check `App::template()` makes of a template's name, on each decoded value, so `match()` now decodes for a path with `..` in it too, not only for one with a `%`. Dots that aren't a segment, like `a..b`, pass. It doesn't cover a value that starts with `/`, or a symlink, since those depend on what the handler does with the value. `file()` covers them where the value becomes a path (see [Files named by a request](#files-named-by-a-request)).
- **Null bytes:** no parameter takes a value with a null byte either, in the same check. No URL has a use for one, PHP's file functions throw a `ValueError` for one, and code in C that a value reaches, like a database driver's, stops reading there, so `report.pdf%00.php` isn't the name it looks like. It arrives only as `%00`: nginx answers a request with a raw one with a 400 before PHP sees it, so `match()` doesn't look for a raw one, which would cost every matched request another search of its path.
- **Cost:** only a path with a `%`, a `\` or `..` runs any of this. `match()` looks for the first two with one `strpbrk()`, in place of the `str_contains()` for a `%`. Looking for the `..` is one more `str_contains()` for each request a dynamic route matches, about 0.01 µs in a loop on the command line. Under php-fpm on macOS, in 7 alternating rounds of 3,000 requests, one took 0.29 µs more inside the worker, with or without a check to run, and a path without one 0.04 µs more, while two copies of the same code differed by up to 0.04 µs.

### Trailing slashes

Every pattern must follow `trailing_slash`, and a pattern that doesn't is a compile error. One case is allowed: when it's `true`, a pattern whose last segment contains a literal dot, like `/feed.xml`, can leave the slash off. Because every route is written in its correct form, the 308 always points at the correct URL. When `trailing_slash` is `false`, catch-alls can't match a trailing slash either, so `/docs/a/` redirects to `/docs/a`.

### How matching works internally

- Static routes use one hash table per method. Each entry is the route's match, ready to return.
- A method's dynamic routes are joined into one regex when PCRE can compile it. The regex is a tree: routes that start with the same path segments share them, and alternatives that start with the same characters share those too, so PCRE reads each part of the path once instead of once per route. Top-to-bottom order still holds, because a route shares an earlier route's branch only when no route in between can match the same path.
- PCRE has to say which route matched. In a regex with up to 12 routes, each route ends in its own number of empty groups, so the number of matches tells them apart, as in FastRoute's `GroupCountBased`. In a larger regex, each route ends in a `(*MARK)` tag. Either way, that key finds the route's match, with the parameter names where their values go.
- When one regex is too large for PCRE, the list of routes is split in half until every part compiles, and a request runs the regexes in order, so top-to-bottom order still holds. Tillkite detects this by checking whether `preg_match( $regex, '' )` returns `false`, not by catching an exception. A temporary error handler takes PCRE's warning.
- Compiling rejects routes that can never match. Because of that, checking the static hash table first gives the same answer as reading the list top to bottom.
- When nothing matches, one check across every method's routes, with and without the trailing slash, settles most misses: a hash lookup and a regex whose routes end in `/?$`. Only a path that some route matches goes on to the exact 405 and 308 checks.
- If `preg_match` returns `false` at request time (for example, by hitting the JIT stack limit), the response is a 500, not a 404, and the failure is logged.

## Running files

- **Scope:** the before-files and the handler run in one isolated function scope that starts with only `$params` and `$tillkite`. They share variables with each other but don't see globals, and nothing they set becomes global. To hand a value from a before-file to the files after it, set a variable. `$tillkite` takes no new properties, so `$tillkite->user = ...` doesn't stick, and reading it back gives PHP's "Undefined property" warning. Two things are still global because that's how PHP works: superglobals like `$_GET`, and any functions, classes or constants the files declare. The files run in a static method of an internal class that has nothing private in it, so there's no `$this`, and `App`'s private members are out of reach. Only code that sets out to, with PHP's Reflection or `Closure::bind()`, can still reach them, and nothing in PHP can stop that.
- **Before-files:** the app's `before` file runs first, then the group's, then the route's own. A group's options, and then a route's, apply to the before-files above them: `before` adds a file after them, `before_only` runs only its own, and `'before' => false` runs none. With no app `before`, a group's or route's own before-file runs by itself. The compiler works out each route's list, as paths, and the runner has a place for each of the three. If a before-file returns `false`, or leaves a status of 300 or more, nothing after it runs, neither another before-file nor the handler. The router sends whatever the before-file produced, such as a redirect, and adds nothing. The status counts because forgetting the `false` is the mistake a login check can least afford: `header( 'Location: /sign-in' )` sets a 302, and without this the handler's page went out in that 302's body, which a browser hides and any other client reads. `App::next_after_before()` checks it with one `http_response_code()`, so it doesn't have to look through the headers, and a route with no before-file doesn't make the call. A status under 300 goes on, like a `Location` with a 201. A status of 300 or more set before `run()`, like a maintenance 503 in `index.php`, stops a route with a before-file too, so the page is empty there. Under php-fpm on macOS, in 7 alternating rounds of 3,000 requests, it adds about 0.2 µs to a request with a before-file and about 0.1 µs to one without, where two copies of the same code differed by up to 0.08 µs. To show an error page instead, a before-file returns `$tillkite->error( 403 )` (see [error()](#error)). See [Why a route's before-file runs after the app's](#why-a-routes-before-file-runs-after-the-apps). They run when no route matches too (see [When no route matches](#when-no-route-matches)).
- **Output:** handlers write their response with `echo` and `header()`. Their return value is ignored.
- **Buffering:** on by default. It means headers can be set at any time, a 500 page always comes out clean, and timing numbers are exact. On an unbuffered route, PHP's usual header rules apply. If a handler ends the buffer itself (`ob_end_flush()`, `fastcgi_finish_request()`), the router copes.
- **HEAD:** a `HEAD` request runs the `GET` handler in full, and PHP drops the body.

## Templates

`$tillkite->template( 'post.php', [ 'post' => $post ] )` runs a PHP file and returns what it printed, so a handler can `echo` it, or pass it to another template, like a layout. It's a helper, not part of routing: it works anywhere, before `run()` too, and a site that never calls it pays nothing for it.

- **Directory:** names are relative to the `templates` option, or the handlers directory when it's empty, or, before `run()` has worked that out, the routes file's directory. Nothing is checked ahead of time, because templates are named in code, not in the routes. A template that doesn't exist is a fatal error from `require`, which names the path.
- **Scope:** `Runner::template()` runs it, as `Runner::files()` runs a handler: a static method of a class with nothing private in it, with the path read with `func_get_arg()`, so the scope starts with only `$tillkite` and `$data`. It doesn't get the handler's `$params` or the before-files' variables, so a template only depends on what it's given.
- **Names:** a name runs a template only when it ends in `.php` and has no `..` segment, with `/` or `\` as the separator, and no NUL byte, so it's a PHP file in the templates directory or a directory in it. PHP's `require` resolves `..` itself, even after a directory that doesn't exist, so `posts/../../.env` would print `.env`, and a file that isn't PHP is printed as it is. Any other name logs, with control characters escaped, and returns `''`. It's checked without touching the filesystem: `str_ends_with()` and two `str_contains()`, and a regex only for a name with `..` in it. A symlink in the directory is the developer's, so it's followed.
- **Output:** `template()` starts a buffer, and returns what's in it. Buffers the template started and didn't end are its output too, so they're ended into it. The route's own buffering doesn't matter, so templates work the same on an unbuffered route.
- **Exceptions:** a `try`/`finally` ends every buffer the template left, throwing away what they hold, and the exception goes on to the caller, or to the 500 file. It catches nothing. Without it, a handler that caught the exception would get the template's half-written output in its page, and on an unbuffered route, so would the 500 page.
- **Timing:** while `run()` is timing the request, each template's own time is a step (see [Timing](#timing)).
- **Cost:** with OPcache, a call to a small template took about 0.35 µs before it was timed, and 0.46 µs after (see [Timing](#timing)). A function written by hand that buffers and requires a file with a fixed path took about 0.21 µs. Of the 0.14 µs more that `template()` took before it was timed, about 0.08 µs is the path: built when it's called, PHP hashes it and looks it up, where a fixed path is hashed once when it's compiled. Runner's extra call, which keeps the scope clean, is about 0.03 µs, and the rest is the default directory and the buffer checks. Requests that don't call it ran 0.04–0.2 µs slower than before under php-fpm, but trunk's own dist file with only its source hash changed ran 0.04–0.13 µs slower too, so most or all of that is where things land in memory. The only new work on that path is comparing `templates` with `''`. Checking the name added about 0.03 µs a call: 0.47 to 0.50 µs, in 7 alternating rounds.

## Sharing values

`$tillkite->register( 'db', $db )` makes a value available to before-files, handlers, error files and templates, which each run in a scope of their own, and `$tillkite->get( 'db' )` returns it. Like `template()`, it's a helper, not part of routing.

- **Values, not functions that make them:** `register()` takes what `init.php` or `index.php` already made, so a variable in `index.php` and what a handler gets are the same thing, and a script in `bin/` that requires `init.php` uses the same variables, with nothing to call. A database connection made there connects on every request, even one that doesn't use it. A site that minds can register an object that connects the first time it's used.
- **Names:** any string. Registering a name again replaces its value. It works anywhere, before `run()` too, so a before-file can register a value for the templates, which don't share its scope, as the handler does.
- **A name with nothing registered:** `get()` logs it and returns `null`, since Tillkite doesn't throw (see [Why Tillkite doesn't throw exceptions](#why-tillkite-doesnt-throw-exceptions)), so using the `null` fails, and the 500 page shows where. A name registered as `null` returns `null` without a log. Only a `null` from the lookup checks `array_key_exists()`, so a value that's there costs one lookup.
- **Types:** `get()` returns `mixed`. A site that wants typed access gives `App` a helper method, like `db() : PDO` (see [Helper methods](#helper-methods)).
- **Cost:** with OPcache, a call to `register()` or `get()` takes about 0.02 µs, and a site that doesn't call them pays nothing but an empty array.

## Files named by a request

The router can turn away a value no URL should have, but it never opens a file, so it can't know that `guide/install` is fine and that `uploads/report`, a symlink someone put there, leads to `/etc/passwd`, or that a handler is about to use a catch-all's `/etc/passwd` as a whole path. That has to be checked where the value becomes a path, which is in the handler, and every site that serves files named by its URLs would write the same check, some of them wrongly. `App::file( $directory, $name )` is that check:

- **What it returns:** the real path of the file, from `realpath()`, when it's a regular file inside the real path of the directory, and `null` for everything else. The handler opens that path, not the name, so what's opened is what was checked.
- **The name:** each part of it, between `/` or `\`, is added to the directory's real path, so the name can never be a whole path of its own: `/etc/passwd` and `php://filter/...` have an empty part, and are `null` before anything is looked up, like a part that's `.` or `..`, which `template()` also turns away. A null byte is `null` too, since `realpath()` throws for one, and Tillkite doesn't throw.
- **Symlinks:** `realpath()` follows every one, in the name and in the directory, and the result has to start with the directory's own real path. A symlink to a file inside the directory is fine, and the path is the file's. One that leads outside, or a file under a directory that does, is `null`.
- **PHP's realpath cache:** PHP keeps what `realpath()` found for `realpath_cache_ttl` seconds, 120 by default, in each worker. A file or directory swapped for a symlink by something other than that worker's own PHP would pass as what it was until then: in a test, `realpath()` still answered with the old path after `mv` and `ln -s`. So `file()` calls `clearstatcache( true, $path )` for each part of the name before it resolves it, which takes those entries out, and costs an `lstat` for each part. What's above the directory isn't forgotten, since the directory is the site's own.
- **What's left:** a swap between `file()` returning and the handler opening the path, which takes write access to the directory and exact timing. PHP has no way to open a file without following symlinks. And it says where a file is, not who may read it.
- **A wrong directory:** a relative one is a mistake in the handler, so it's logged, like a name with nothing registered for `get()`, and gets `null`. A name that gets `null` isn't logged, since requests for files that aren't there are ordinary, and a log line for each would let a visitor fill the log.
- It has no state and works before `run()`, like `template()`. It's a method of `App`, not a class of its own like `Escape`, because a handler already has `$tillkite`, and it's one call.

## Escaping

`Tillkite\Escape` has a static method for each place text goes in a page, and one to set the page's encoding. Each returns a string and never throws. Like `template()`, it's a helper, not part of routing, and works without an `App`. The README tells developers to write `use Tillkite\Escape as Esc;`.

- **`html( string|int|float|\Stringable|null $value )`:** `htmlspecialchars()` with `ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML401`, and `'UTF-8'` named, so the `default_charset` setting can't change it. For text between tags, and safe in a quoted attribute value. For UTF-8 it calls `htmlspecialchars()` itself, not the helper the other methods share, which would take a quarter of its time. From 48 bytes, UTF-8 text that `preg_match( '//u' )` finds valid goes through `strtr()` with the five characters instead, which gives the same output in far less time for each byte. The check costs as much as `htmlspecialchars()` takes for about 16 bytes, so shorter text, with many of the five, is faster the other way: timed against 0.0.5, text of 48 bytes takes up to 67 ns less, but none less with six of the five in it, 128 bytes takes 225 to 265 ns less, and shorter text about 4 ns more, for the length check. Invalid UTF-8 needs `htmlspecialchars()`, which replaces it with U+FFFD. A CR comes out as it is, and the HTML parser reads it as a LF, as it reads every CR in a page, while `html_attr()` escapes it, so it stays a CR.
- **`html_attr()`:** `html()`, then `strtr()` with tab, LF, FF, CR, space, `=` and the backtick as numeric entities, so it's safe in an attribute value with or without quotes (see [Why html_attr() escapes only a few more characters](#why-html_attr-escapes-only-a-few-more-characters)). In UTF-8, it calls `htmlspecialchars()` itself, and from 24 bytes, valid UTF-8 goes through one `strtr()` with both tables, which saves a second `strtr()` too, so it breaks even sooner than `html()`. Timed against 0.0.5, it takes 10 to 15 ns less below 24 bytes, up to 125 ns less at 48 bytes, and 335 to 370 ns less at 128, but text of 24 bytes with six of `& < > " '` in it is no faster. `url()` does the same, and takes 15 to 20 ns less below 24 bytes and 340 to 375 ns less at 128. Without quotes, an empty value lets the parser take the next attribute as its value, so the README says to quote an attribute that can be empty. It's for text: a URL, code or CSS in an attribute needs `url()`, `js()` or `css()` first, and text in `srcdoc`, which holds a page, needs `html()` first.
- **`url( string $url, array $schemes = [ 'http', 'https', 'mailto', 'tel' ] )`:** for a whole URL in an attribute. It takes out what the WHATWG URL parser takes out before it reads a URL, the C0 controls and spaces at either end and every tab, LF and CR, then reads the scheme by the parser's rule: a letter, then letters, digits, `+`, `-` and `.`, up to a `:`. If there's a scheme, and its lowercase form isn't in `$schemes`, the URL becomes `about:invalid`. Then it's escaped as `html_attr()` escapes. A relative URL has no scheme, so it's allowed. It doesn't percent-encode: the browser does that for what needs it. Laminas's and Phalcon's `escapeUrl()` is `rawurlencode()`, for one part of a URL, which PHP already has, and neither stops a `javascript:` URL.
- **`js( mixed $value )`:** `json_encode()` with `JSON_HEX_TAG`, `JSON_HEX_AMP`, `JSON_HEX_APOS`, `JSON_HEX_QUOT`, `JSON_UNESCAPED_SLASHES`, `JSON_INVALID_UTF8_SUBSTITUTE` and `JSON_PARTIAL_OUTPUT_ON_ERROR`, which writes each character outside ASCII as a `\uHHHH` escape, then `strtr()` on each string with the 28 ASCII characters that `json_encode()` leaves as they are, but letters and digits, as `\uHHHH` escapes too (see [Why js() escapes more than JSON needs](#why-js-escapes-more-than-json-needs)). So the output is all ASCII, and its strings hold only letters, digits and escapes. With `JSON_HEX_QUOT`, a string never holds a raw `"`, so every `"` starts or ends one, and `explode()` on `"` puts each string's contents in every other piece. That takes a fifth less time than the regex `/"[^"]*+"/` with a callback for each string did: 950 ns for a record with four keys, against 1,190, and 14.0 µs for a list of 20, against 17.7. When the value is a string, the whole output is one string, so `strtr()` takes it as it is. Without `JSON_UNESCAPED_SLASHES`, `json_encode()` would write `\/`, and the table would turn its `/` into an escape after the `\`. With `JSON_PARTIAL_OUTPUT_ON_ERROR`, `json_encode()` never returns `false`: what JSON can't hold becomes `0` or `null`, and `js()` logs `json_last_error_msg()`. So an enum without values is logged and becomes `0`. A `Stringable` object is its public properties, like any other object, and a float is written as `serialize_precision` says, which by default is as JavaScript writes it. Two keys that differ only in invalid UTF-8 become the same key, and the later one wins in JavaScript. A key named `__proto__` sets an object's prototype in JavaScript code, though not in `JSON.parse()`, so the README says to put data with keys from a visitor in `<script type="application/json">`.
- **`css( string $value )`:** `strtr()` with the 66 ASCII characters that aren't letters or digits as six-digit escapes, like `\000020`, and a digit at the start as `\00003` and the digit, since a name can't start with one. Six digits end an escape, so a letter or digit after it is never read as part of it. But CSS takes in one whitespace character after an escape, even after six digits, so when the output ends with an escape, `css()` adds a space, and a space written after the output stays. Laminas writes `\20 `, with a space after every escape, and leaves a digit at the start as it is. NUL becomes `\000000`, which CSS reads as U+FFFD, as it reads every NUL, and an empty value gives an empty string, which isn't a valid name. Invalid UTF-8 is replaced with U+FFFD first, by a trip through `htmlspecialchars()` with `ENT_SUBSTITUTE` and back, so it doesn't need mbstring.
- **`log( string|int|float|\Stringable|null $value )`:** for text in a log line, which someone reads in a terminal or an editor. `addcslashes()` turns the C0 controls and DEL into C-style escapes, like `\n` and `\033`, so text can't send a terminal a command, like ESC's, or start a line that looks like another entry. In valid UTF-8, a regex turns the C1 controls, U+0080 to U+009F, which some terminals take as commands too, and the characters that make an editor show text in another order or on another line, U+061C, U+200E, U+200F, U+2028 to U+202E and U+2066 to U+2069, into `\u{202E}` escapes, with the code point worked out by hand, since UTF-8 doesn't need mbstring. Text that isn't valid UTF-8 has each byte from 0x80 escaped, like `\233`, since a terminal in another encoding could read a lone 0x9B as a C1 control. `\` stays as it is, so paths and regexes read as they are, which means a `\n` already in the text looks like an escaped newline, but can't do anything. `set_encoding()` doesn't change it. Every line Tillkite logs with text it didn't write itself goes through it: a template's name, a name `get()` didn't find, an encoding `set_encoding()` doesn't take, a cache write's warning, configuration problems, and an uncaught exception after the output started, which so becomes one line. The starter's 500 file logs `$error` through it too.
- **`set_encoding( string $encoding ) : bool`:** the page's encoding, UTF-8 by default. It takes 18 names from the WHATWG Encoding Standard, in any case, and maps each to mbstring's name for the encoding browsers read it as: a page that says `iso-8859-1` is read as windows-1252, so that's what it's converted from. Browsers read `gbk` as gb18030, and `euc-jp` with the NEC and IBM characters that mbstring calls eucJP-win. mbstring still reads a few characters differently from browsers, mostly in Big5 and EUC-JP, and some invalid bytes too: it takes a Shift_JIS first byte and the `"` after it as one `?`, where a browser reads U+FFFD and the `"`. Since the output is all ASCII, that changes how text looks, never what the page does. Another encoding needs mbstring, and a name it doesn't take, or no mbstring, is logged and returns `false`, and the encoding stays as it was. Each method then converts its text from that encoding to UTF-8 with `mb_convert_encoding()`, escapes it, and makes every character outside ASCII an escape: `mb_encode_numericentity()` for `html()`, `html_attr()` and `url()`, and six-digit escapes for `css()`, while `js()`'s output is always ASCII (see [Why another encoding's output is all ASCII](#why-another-encodings-output-is-all-ascii)). Before the references, U+0080 to U+009F become U+FFFD, because HTML reads `&#128;` to `&#159;` as windows-1252's characters, so no reference can be one of them, and a C1 control from ISO-8859-2 would show as `€` or `“`. `url()` checks the scheme after converting, because mbstring can take out bytes it can't read, with `mbstring.substitute_character` set to `none`, which would turn `java\x81script:` into `javascript:` after a check of the bytes passed it. `js()` converts the strings and keys in arrays itself, because `mb_convert_encoding()` drops an object in an array, with a warning. It goes as deep as `json_encode()` does, 512 arrays, so an array that holds itself ends, and `js()` logs it. An object's strings have to be UTF-8 already.
- **Cost:** with OPcache, `html()` of a name takes about 0.06 µs, 0.02 µs more than `htmlspecialchars()`, and `html_attr()` 0.13 µs. `url()` takes about 0.46 µs, `js()` of a name 0.13 µs and of a small array about 1 µs, and `css()` of a name 0.27 µs. The class adds about 11 KB to the dist file.

`tests/escape-tests.php` parses each method's output with PHP's `Dom\HTMLDocument`, an HTML5 parser that follows the standard as browsers do, and checks that values meant to break out of where they're printed come back as they were, with no element or attribute of their own: as text, and in double-quoted, single-quoted and unquoted attributes. It checks that `js()` decodes to the value, is all ASCII and has only letters, digits and escapes in its strings, that `css()` has only letters, digits and six-digit escapes, with no digit at the start and a space after a last escape, a URL with each way of hiding its scheme, each encoding, with bytes that start a longer character before `"`, `\` and `'`, and an array that holds itself.

While the class was being built, another agent attacked it as a red team. It ran 9,120 checks of `html()` and `html_attr()` in PHP's HTML5 parser, as text, in `<title>`, `<textarea>`, SVG and MathML, and in each kind of attribute; 80,000 random URLs through the HTML5 parser and node's WHATWG URL parser; 1,908 `js()` cases, in `<script>`, `JSON.parse()`, `onclick` and quotes put around it by mistake; 154 `css()` values in Chromium; and 357,000 runs of random bytes in each encoding, with each kind of `mbstring.substitute_character`. It found one way to run code: `js()` left characters outside ASCII as they were, so in quotes put around it by mistake, a value with U+00A0 between its words called a function (see [Why js() escapes more than JSON needs](#why-js-escapes-more-than-json-needs)). It also found that `css()` left a digit at the start and let CSS take in a space after its last escape, that C1 controls in another encoding showed as other characters, that `gbk` and `euc-jp` were converted as encodings browsers don't use, and that `js()` converted arrays without a limit, so an array that held itself never ended. Each is fixed and has a test, and the rest are documented above and in the README.

## Errors

Tillkite never throws exceptions and never uses `try`/`catch`. It defines no exception classes.

### Configuration problems

Problems with the options or the route list are mistakes by the developer, so Tillkite collects them as a list of messages instead of throwing:

- an unknown option key in the constructor, or a value of the wrong type,
- setting a property that doesn't exist (caught by `__set()`),
- no `routes`, a relative path for `routes`, `handlers` or `cache`, or a `base` that doesn't start with `/` or ends with one,
- a `handlers`, `templates` or `cache` directory inside the document root (see below),
- a routes file that doesn't exist or doesn't return an array,
- a `cache` directory that doesn't exist, belongs to a user Tillkite doesn't trust, or that PHP can't write to (see [Route cache](#route-cache)),
- every compile error in the route list (see [Compile errors](#compile-errors)).

When there are any, `run()` responds with a 500. Under `php -S` the response lists every problem. Anywhere else, such as php-fpm, they're written to the error log, each starting with `Tillkite: `, and the 500 file runs with `$error` describing them. If the problems leave no 500 file to run, a plain 500 is sent. They show up on the first request under `php -S`, or in CI when a test requests a page.

**Directories inside the document root:** a file there can be requested by its own path. `php -S`, and Apache as most hosts set it up, would run a handler that way, without its before-files, so a login check in one never runs, and a server that doesn't run it sends its source. Either sends what else is in the cache directory, like a SQLite database. A site built by hand on a host whose document root is the site's own directory ends up this way without anyone choosing it. So `App::check_document_root()` compares the resolved `handlers`, `templates` and `cache` directories with the resolved `DOCUMENT_ROOT`, and reports each one that's inside it. It runs only when the routes are compiled, which a site with a cache does once, and problems are never cached, so the site answers with a 500 until the directory moves. There's no option to turn it off. It can't see a server that's told not to serve those directories, and it trusts `DOCUMENT_ROOT`, which an Apache `Alias` or a missing `fastcgi_param` leaves wrong or empty, and then nothing is reported. It reads it from `$GLOBALS['_SERVER']` when something has built that, or from `getenv()`, and not through `App::server()`, whose `filter_input()` would build `$_SERVER` for a server that passes none (see [Why Tillkite's code never names $_SERVER](#why-tillkites-code-never-names-_server)). The command line has none. The routes file isn't checked: requested directly, it returns its array to nobody.

**Problems with the site's setup:** `App::setup_problem()` adds a problem that whoever put the site on its server has to fix before it's safe to run: a description of what's wrong and what to do, without a path, and the paths, which follow it in the problem's message. Outside `php -S`, when there are any, the response is a plain-text 500 that lists the descriptions, under "This site isn't set up safely, so Tillkite won't run it", and ends with "The error log has the details", and the site's 500 file doesn't run. Its page is for visitors and says nothing of this, and a developer on a new server may not know where its error log is yet. The page goes to every visitor until the problem is fixed, so it has no paths, but it does tell them the site is set up unsafely, and how. That's the price of the developer seeing it: the site isn't answering anything else, so the state doesn't last, and the paths stay in the log. Under `php -S` the response lists every problem in full, as before.

### When no route matches

When no route matches, the before-files run first, and then the response: a 308 redirect, or the 404 or 405 file, or plain text. For a path under a group's prefix, they're the before-files a route in the group with no options of its own would run, and the group's error files take the place of the app's for the codes it lists (see [Groups](#groups)). Otherwise, they're the app's before-file and error files.

- So a login check in a before-file covers every path under its prefix. Without it, a visitor it turns away could still tell which paths exist: a route for another method gets a 405 with an `Allow` header, and a route with the other trailing slash gets a 308, but a made-up path gets a 404. And the headers a before-file sends, like security headers or a JSON `Content-Type`, go out with the error page.
- They run as they do for a route, in one scope, but `$params` holds the parameters of the group's prefix, or nothing, and `route()` returns `null`, which tells them no route matched. They're always buffered, whatever `buffer` says, because what they print is thrown away.
- If one returns `false`, or leaves a status of 300 or more, nothing after it runs, and what they printed is sent. If one calls `error()`, its page is shown, as for a route. Either way, the 405's `Allow` header and the 308's `Location` never go out.
- Otherwise, what they printed is thrown away, and the response goes ahead. The 404 and 405 files run in a scope of their own, with the prefix's parameters in `$params`.
- The runner runs them with no handler after them. The callback into `App` that runs before the handler returns `false`, and notes that they all ran.

See [Why misses run the before-files](#why-misses-run-the-before-files).

### error()

A before-file or handler shows an error page with `return $tillkite->error( 404 );`. It takes the standard 4xx codes other than 405, whose `Allow` header only the router knows. A 500 comes from throwing an exception, which gives the 500 file the real error.

- `error()` records the code and returns `false`. It doesn't stop the file that called it, since that would take an exception or `exit`.
- Once that file returns, no file after it runs. Before each before-file after the first, and before the handler, the runner calls back into `App`, which says to stop once a code is recorded. So a before-file that leaves off the `return` still stops the handler. Returning the `false` stops it the usual way, and also skips the rest of the file.
- Then what's buffered is thrown away, the status is set, and the file for that code in the route's group's `errors` or the app's runs, or plain text is sent, like `403 Forbidden`. The error file runs in a scope of its own, with the route's `$params`. Headers the files set stay.
- Only the first call counts. A call anywhere but the before-files and handler, such as from an error file, does nothing, and is logged.
- A code that `error()` doesn't take is logged, and the response is a 500, which runs the 500 file with `$error` describing it.
- On an unbuffered route that has already sent output, nothing can be taken back, and the status can't change. The call is logged, and nothing is added.

See [Why error() waits for the file to return](#why-error-waits-for-the-file-to-return).

### The 500 file

- The 500 file runs for every 500: Tillkite's own, a `preg_match` failure while matching or configuration problems outside `php -S`, and any exception that a before-file, a handler, or the 404 or 405 file doesn't catch. It catches those exceptions with `set_exception_handler()`. Tillkite registers that handler only when a 500 file is set, the app's or that of the group of the matched route or of the miss, and it replaces any exception handler the app registered before `run()`. The group's 500 file takes the place of the app's.
- For an exception, `$error` is the uncaught exception. It's always thrown by the app's own code or by PHP itself, such as a `TypeError`, or a `ParseError` from a syntax error in an included file. For Tillkite's own 500s, it's a `RuntimeException` that describes the failure, which Tillkite creates but never throws.
- On a buffered route, any output already produced is thrown away, the status is set to 500, and the 500 file runs.
- On an unbuffered route that has already sent output, the error is logged and the 500 file's output is appended.
- If the 500 file itself throws, that's a fatal error.

### Fatal errors

Running out of memory or time, a compile error such as declaring a function twice, and an uncaught exception with no 500 file to catch it are fatal errors. They end the request without reaching the 500 file. PHP logs them as usual, and a shutdown function that `run()` registers sends the response:

- What's still buffered is thrown away, and a plain-text 500 with one line of text is sent.
- With `display_errors` on, PHP's message is in the buffered output, so that output is sent with a 500 instead. `run()` turns it off outside `php -S` and the command line, so elsewhere this takes a host that locks the setting or disables `ini_set()`, or a file that turns it back on.
- Output that's already been sent can't be changed.
- Running out of memory, PHP throws the buffered output away itself. With `display_errors` on, it then sends its message with a 200 before the shutdown function runs.

### PHP's error settings

With no `php.ini`, as in PHP's official Docker image, `display_errors` is on. Under php-fpm, a warning in a handler put the handler's full path on a page with a 200, an uncaught exception with no 500 file put its message, paths and stack trace with arguments on a page with a 500, and an exception before `run()` put its message on a page with a 200.

- **`run()`** calls `ini_set( 'display_errors', '0' )` as it starts, outside `php -S`, for the developer, and the command line, where no visitor reads the output. It's the same line the 500 file and the configuration report draw between development and production. It checks `function_exists()` first, because calling a function that a host's `disable_functions` lists is a fatal error. A file that runs after it can turn the setting back on, and `php_admin_flag` makes `ini_set()` do nothing. It adds 0.08 µs a request under php-fpm on macOS, in 7 alternating rounds of 3,000 requests, while two copies of the same code differed by up to 0.04 µs.
- **`run()` can't reach what comes before it,** like a database connection in `init.php`. So the `public/index.php` that `new` makes, and the example site's, start with the settings for production, again outside `php -S`: `display_errors` and `html_errors` off, `log_errors` and `zend.exception_ignore_args` on, the session cookie's `httponly`, `samesite=Lax` and `secure`, `session.use_strict_mode`, and `header_remove( 'X-Powered-By' )`, since `expose_php` can't be set from code. With `run()`'s line, they add 0.46 µs a request inside the worker, and 0.71 µs at the client, 1.4%. They're in the site's own file, not in `run()`, so a site can see and change them, and a site that doesn't use sessions can drop those lines. `session.cookie_secure` stops sign-ins from working over plain HTTP, which fails where someone will notice, and the comment above it says so.
- **What code can't do:** a parse error in the front controller comes before any of its lines run, and `expose_php`, `allow_url_fopen` and `allow_url_include` can't be set at run time, so the README's Deploying section gives them for `php.ini`. With `session.auto_start` on, each `ini_set()` of a session setting logs a warning, because the session has already started.

### Other failures

Tillkite checks return values for its own failures:

- `preg_match` returning `false` at request time: the failure is logged, and the 500 file runs, or a plain 500 is sent.
- A cache file that can't be written, in a directory that's there and that PHP can write to, like on a full disk: routes are compiled in memory and a warning is logged.

## Timing

Each request is always timed with `hrtime()`, in these steps:

| Step | What it measures |
|---|---|
| `total` | From the start of `run()` until the response is finished |
| `route` | From the start of `run()` until the first file runs, including loading the cache or compiling routes |
| `before` | The before-files: the app's, the group's, then the route's |
| `handler` | The handler |
| `error` | The error file: the 404 or 405 file, the file for `error()`, or the 500 file |
| `template:NAME` | A template that `template()` ran, like `template:layout.php`, without the templates it ran |

`$tillkite->timings()` returns milliseconds for each step that ran. A step that's still running reports its time so far. A step that runs twice, such as a 404 file that throws and then the 500 file, reports the sum.

```php
[ 'total' => 13.566, 'route' => 0.004, 'before' => 1.217, 'handler' => 12.345 ]
```

A typical use is a shutdown function registered in the before-file that logs slow requests along with `$tillkite->route()`. `run()` registers Tillkite's own shutdown function before any file runs, so by the time the app's runs, the timing has stopped.

Each step records only its start time, because it ends when the next one starts. Timing costs about 0.25 µs per request, so it's always on.

A template's time is a step of its own while `run()` is timing the request. `template()` starts the template's step, and when the template returns, or throws, starts again the step that ran it, which `Timer::next()` returns. So `before`, `handler` and `error` don't have the time of the templates they ran, a template's step doesn't have the time of the templates it ran, and the steps still add up to `total`. A template that runs more than once has the sum, as other steps do. Before `run()`, or once the response is finished, as in a shutdown function, a template isn't timed, because a step that started after the end would have a negative time.

```php
[ 'total' => 1.2, 'route' => 0.004, 'handler' => 0.9, 'template:layout.php' => 0.052, 'template:nav.php' => 0.011 ]
```

Timing a template costs about 0.12 µs a call: a call took about 0.34 µs without it and 0.46 µs with it, under the CLI with OPcache. Most of it is the two `hrtime()` calls and the two steps added to the timer's arrays. Keeping the name of the running step in a property, instead of reading the last one with `end()`, saved about 0.05 µs, because `end()` takes the array by reference.

### Server-Timing header

When `server_timing` is `true`:

```
Server-Timing: tillkite-total;dur=13.566, tillkite-route;dur=0.004, tillkite-before;dur=1.217, tillkite-handler;dur=12.345
```

- Each metric is named `tillkite-` plus the step name, so it can't be confused with other entries. A template's is `tillkite-template`, with the template's name in `desc`, like `tillkite-template;desc="layout.php";dur=0.052`, because a name can have characters a metric's name can't, like `/`. So the header names the templates a page ran. `desc` is a quoted string, with `"` and `\` escaped, and anything in the name that isn't printable ASCII, and `%`, percent-encoded, like `%0A`, so the header holds only what HTTP allows. PHP's `header()` refuses a value with a newline, which would drop the whole header.
- The router adds its header with `header( ..., false )` and never replaces existing ones. Handlers add their own entries the same way.
- The header has the steps that have finished when it's added. It's added once, as late as it can be:
  - after the handler on a buffered route, and after a buffered 4xx file,
  - just before the handler on an unbuffered route, so it has only `route` and `before`, and just before an unbuffered 4xx file,
  - just before the 500 file, which isn't buffered, so it has the steps before it but not `total`,
  - before the text of a plain-text response, and with a redirect,
  - from a shutdown function, when a file calls `exit` or a fatal error ends the request.
- If the headers have already gone out, for example because an unbuffered before-file printed something, there's no header.
- It's off by default because timing data visible to every client can leak information, such as a login check that's slower for usernames that exist.

## Route cache

When `cache` is set:

1. On each request, Tillkite reads the routes file's modification time, change time and size with one `stat` call, and the cache directory's mode with another. The cache file's name is a hash of those, the routes file's path, the settings that change what the routes compile to or the problems found (`handlers`, `before`, `trailing_slash`, `methods` and `errors`), Tillkite's version, a hash of Tillkite's code and PCRE's version. Under `php -S`, it also has the modification time and size of each of Tillkite's own files. Tillkite includes that file, without checking that it exists first, which would be a third `stat`.
2. If that file isn't there, Tillkite:
   1. clears the routes file from OPcache with `opcache_invalidate()`, so a stale copy is never compiled,
   2. compiles the routes,
   3. writes the cache to a temporary file, sets its modification time a minute in the past so OPcache caches it right away, and renames it into place,
   4. removes the routes file's older cache files from the directory,
   5. includes the new cache file, so this request matches with OPcache's copy of the routes, like every later one (see [Why the compiler checks copies of its regexes](#why-the-compiler-checks-copies-of-its-regexes)).
3. Routes with problems aren't cached, so the problems are reported on every request until they're fixed.
4. A cache directory that doesn't exist, or that PHP can't write to, is a problem with the site's setup (see [Configuration problems](#configuration-problems)), found when the routes are compiled, so a site with a cache pays nothing for the check. Otherwise the routes would be compiled on every request, with a line in the log each time: about 0.5 ms a request for the example site's routes, and 13.7 ms for the GitHub API's 1,259, against well under a microsecond to read them from the cache. `Cache::setup_problem()` checks with `is_dir()` and `is_writable()`. If the cache file can't be written for another reason, like a full disk, Tillkite compiles the routes for that request and logs a warning, so the site goes on working.

The rule: **change the routes file, a file it loads, a setting or Tillkite's code, and the next request rebuilds the cache.**

- The cache is plain data, strings and arrays only, so OPcache keeps it in shared memory. It keeps each route as `route()` returns it, and the paths of the before-files each route runs, so a request doesn't work them out.
- Several php-fpm workers may rebuild at the same moment after a change. That's safe, because each writes its own temporary file, they write the same content, and the rename is atomic.
- Each cache file's first line names its routes file by a hash of the path, so apps that share a cache directory only remove their own older files.
- `App::SOURCE_HASH` is a hash of every file in `src/`, with its own value left out. `make dist` writes it into `src/app.php`, and CI fails if it's out of date. So someone running Tillkite from a commit between releases never reads a cache that older code wrote, in a format the new code doesn't read, which made every request a 500. Under `php -S`, the key also has the modification time and size of each of Tillkite's files, which costs a `stat` for each, there only, so editing Tillkite while the example site runs never reads an old cache. See [Why the cache key has a hash of Tillkite's code](#why-the-cache-key-has-a-hash-of-tillkites-code).
- A stale route table is a security problem, since a route's before-files are in it: a login check added to a route that's still cached doesn't run. So:
  - **Files the routes file loads:** `App` notes which files `get_included_files()` gains while the routes file runs, and the cache file keeps each one's modification time, change time and size in `includes`. `Cache::read()` compares them, with one `stat` for each, and a site that loads none pays for one `empty()`. A change, or a file that's gone, reads as no cache, so the routes are compiled again and written under the same name. A file that's gone fails when the routes file requires it, as a fatal error, and the handler doesn't run.
  - **Edits that keep the modification time:** the change time is in the routes file's key and in each stamp, because a deploy like `rsync -t` keeps the modification time, and an edit can keep the size, but nothing can set the change time. OPcache looks only at the modification time, so a changed file is taken out of it with `opcache_invalidate()`. On Windows, PHP's change time is the creation time, so only the modification time and size count there.
  - **OPcache's copy:** after an edit, OPcache can give the routes file the old copy of a file it loads for up to `opcache.revalidate_freq` seconds. Caching that under the new file's stamp would keep the old routes until the next change, so `Cache::stamps()` returns `null` for a file that changed that recently, and the routes are compiled on every request until then, without being written. The new routes are in use from the first request, except that a file OPcache hasn't been told about, because the routes file changed in that same window and is what loads it, can be served old until OPcache checks it. Then the cache file is taken out of OPcache too, or requests would keep reading the old one. Without that, one site still compiled on 206 of 209 requests six seconds after an edit.
  - **What it can't see:** anything that doesn't run as a file while the routes file does, like a JSON file or the result of `glob()`, and a file that was loaded before `run()`, like one that `init.php` requires.
  - **Cost:** under php-fpm on macOS, in 7 alternating rounds of 3,000 requests, reading the change time adds 0.12 to 0.21 µs to a request on a site with a cache, in two runs, while two copies of the same code differed by up to 0.04 µs. Using it in place of the modification time would cost nothing, but would need another path for Windows, and the local tests would have to wait for a new second after every edit. A site whose routes file loads one file pays 1.46 µs in all.
- Handler, before and error files are checked when the routes are compiled. One removed after that fails when it runs, as a fatal error.
- The cache directory must exist, be writable by the web server, and be outside the document root, because the cache is PHP that gets executed.
- The cache directory must not be writable by every user, who could put PHP in it for the web server to run, or make the cache file before it does, even with the sticky bit. `Cache::read()` checks the directory's mode before it includes the file, and `Cache::write()` before it writes one, so in such a directory a planted file never runs, nothing is written, the routes are compiled on every request and each one logs why. The check has to be on every read, since the attack is a file that's there before the first write. It's one `stat`, and costs 1.25 µs a request under php-fpm on macOS, taking a small site's time inside the worker from 5.9 to 7.2 µs and the client's latency from 52 to 53 µs, while two copies of the same code differed by 0.04 µs. A site without `cache` doesn't pay it.
- The cache directory must belong to root, to the user PHP runs as, or to the routes file's owner, who can change the site's PHP anyway. A directory that was missing, under a parent that lets anyone make one, like `/tmp`, could be made first by another user, as 0755, which the check above passes, with a file in it under the cache file's name. That name is a hash of what any local user can read: the routes file's path, times and size, the options in `index.php`, Tillkite's version and source hash, and PCRE's version. `Cache::directory_problem()` reads the owner from the same `stat` as the mode, through PHP's stat cache, and the routes file's owner from the `stat` its key already takes. The user PHP runs as comes from `posix_geteuid()`, which is asked only when the owner is neither of the others. Without the posix extension there's no telling, so only root and the routes file's owner pass. On Windows the owner is always 0. It doesn't look at the directories above it, or at who is in the directory's group. `Cache` never reads or writes such a directory, which alone would leave the site compiling its routes on every request, with a line in the log each time, for as long as nobody read it. So `App` asks `Cache::setup_problem()` when the cache has nothing to read, and reports what it says as a problem with the site's setup (see [Configuration problems](#configuration-problems)): a 500 on every request, whose page says that the directory belongs to another user, or that without posix Tillkite can't tell, and which owner to give it or to load the extension. A directory that every user can write to is still only logged and not used: on Windows, PHP reports every directory that way, so making it a problem would stop every site with a cache there. Each cache file is `chmod()`ed to 0644 before it's renamed into place, whatever the umask. `new` adds 002 to the umask while it writes, so nothing it makes is writable by every user, and a umask that already leaves out group or world write is kept.

### Compile errors

Compiling reports each of these as a configuration problem, with the route's or group's position in the list and the entry itself (see [Groups](#groups) for how routes in a group are numbered):

- a route that can never match because an earlier route covers it (always caught when the hidden route is static, best effort when both are dynamic), including an explicit `HEAD` route below a `GET` route for the same path,
- a duplicate route,
- a pattern too large for PCRE to compile, reported once, without PCRE's offset, which points into the joined regex, not the route's pattern, and differs between PCRE versions,
- an invalid pattern: unbalanced braces or brackets, an optional part that isn't at the end or is empty, a capturing group, a `(*...)` verb or an invalid regex, a duplicate, empty or invalid parameter name, or a missing leading `/`,
- a pattern that doesn't follow `trailing_slash`,
- a malformed route entry: not three or four elements, or an unknown route option,
- an unknown or lowercase method, or `'*'` combined with other methods,
- a missing handlers directory, handler, before-file or error file,
- a group or route that sets both `before` and `before_only`, a `before_only` that isn't a file name, or a `before` file that already runs, as the app's or the group's, which would run twice,
- a group without a prefix that starts with `/` and doesn't end with one, a prefix with optional parts or an invalid parameter, routes that aren't a list, an unknown group key, a group inside a group, or a pattern in a group that doesn't start with `/` or `[` and isn't `''`,
- an error code in the app's or a group's `errors` other than 500 or a standard 4xx code, or an error file that isn't a file name, or a custom method in `methods` that isn't uppercase.

## php -S and php-fpm

Behavior is the same under both, with two differences:

- **Static files:** under `php -S`, `run()` returns `false` for an existing file inside the document root, other than the front controller itself or any other PHP file, so `php -S` serves it. `php -S` runs a PHP file it's left to serve, without the before-files, so one is routed like a path for no file, whether the path or the file it resolves to ends in `.php`, in any case, and the front controller is the only PHP a request runs, as with the nginx configuration above. The front controller is the file at the bottom of the call stack, because the first included file is a file from `auto_prepend_file` when that's set. It checks this before routing, and confirms the resolved path is inside the document root so `..` can't reach other files. Under php-fpm, the web server serves static files.
- **Configuration problems:** under `php -S` they're listed in the 500 response. Under php-fpm they're logged.

## Deploying

There is no build step. Deploy the files, and the first request after the routes file changes rebuilds the cache.

PHP's settings for production are in [PHP's error settings](#phps-error-settings).

**Copying files in place (default):**

- `opcache.validate_timestamps=1` and `opcache.revalidate_freq` of 2 seconds or more. OPcache checks each file at most once per interval, shared across all workers.
- Copy handler files before the routes file, so new routes never point at files that aren't there yet.

**One directory per release:**

- `opcache.validate_timestamps=0`. Each deploy goes into `releases/<id>/`, and a `current` symlink switches to it.
- The web server must pass the resolved path. For nginx:

```nginx
root /var/www/current/public;
fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
fastcgi_param DOCUMENT_ROOT   $realpath_root;
```

- Give `opcache.memory_consumption` room for a few releases.

## Design notes

Measurements below were taken on PHP 8.5.4 with PCRE2 10.47 and JIT on.

### Why one regex, split in half as the fallback

A single combined regex has a size limit. With routes shaped like `/section{n}/items/{x}/comments/{id:\d+}`, one regex compiled with 774 routes and failed at 775 ("regular expression is too large"). Shorter patterns fit more. The limit depends on pattern length and on how PCRE was built, so it must be detected, not hard-coded.

FastRoute splits routes into fixed groups of about 30. Symfony starts with one regex, halves on failure, and nests shared prefixes. Grouping by first path segment was fastest for 1,000 dynamic routes (50 resources × 20 routes):

| Approach | Regexes | First route | Middle | Last | Miss |
|---|---|---|---|---|---|
| Fixed groups of 30 (FastRoute) | 34 | 0.13 µs | 1.77 µs | 6.42 µs | 2.69 µs |
| As few regexes as will compile (Symfony) | 1 | 0.79 µs | 1.04 µs | 1.80 µs | 1.36 µs |
| Grouped by first path segment | 50 | 0.15 µs | 0.17 µs | 0.21 µs | 0.04 µs |

Real-world APIs often share a first segment, and first-segment grouping wasn't enough there: hundreds of GitHub API routes start with `/repos/`, and that group's regex took 1.75 µs on its own. Building each regex as a tree of shared prefixes fixed that, and changed the answer. A tree's cost depends on the path rather than on the number of routes, so one regex for the whole table is fastest. Every table in the GitHub and Stripe sets fits in one regex (GitHub's `GET` is 14 KB); the 5,000-route set's `GET` table is the one that doesn't.

First-segment groups stayed as the fallback for a table like that, until the trees made them redundant too. Split in half, the 5,000-route set's `GET` table is 2 regexes instead of 500 groups, and a path that the first one doesn't match fails it within its first segment. Timed on PHP 8.5.4, matching every 25th route of that set took 0.144 µs on average and 0.265 µs at most, against 0.146 and 0.261 µs with the groups, its last route took 0.02 to 0.06 µs more, for the one regex it fails first, and its cache file went from 2,314 to 2,159 KB. A 405 or a 308, which run several tables, took 0.1 to 0.2 µs less on the smaller sets, since each table no longer checks which kind it is. So the groups went, with the hash table of first segments, the matcher's check for one on every dynamic match, and the copy of each route with a parameter for its first segment in every group. Each further regex that a larger table needs would cost the routes after it about as much again.

### Why Tillkite's code never names $_SERVER

With `auto_globals_jit`, which is on by default, PHP builds `$_SERVER` from everything the web server sent the first time a compiled file names it, and OPcache builds it each time it loads a file that names it, even in code that never runs. So loading `app.php`, or the dist file, built `$_SERVER` on every request, before `run()` started, so neither the step table above nor `Server-Timing` counted it. Timed inside one php-fpm worker with nginx's FastCGI parameters and a browser's headers, a file that names `$_SERVER` in a function it never calls took 3.8 µs to load, against 0.1 µs for one that doesn't.

So `run()` and the miss path read `$GLOBALS['_SERVER']['REQUEST_URI']`, which doesn't build it, and fall back to `App::server()` when nothing has. That reads `getenv()`, which under php-fpm has the request's values, and under `php -S`, where `getenv()` has none, calls `filter_input( INPUT_SERVER )`, which builds `$_SERVER` and returns `null`, so the value comes from `$GLOBALS` after all. A site that has built `$_SERVER`, and may have changed it, is read from `$GLOBALS` without a call. The dist file's footer reads `$GLOBALS['_SERVER']`, which the CLI builds before it runs a script.

`DOCUMENT_ROOT`, for the check of directories inside it, doesn't go through `App::server()`. Unlike the request's URI and method, a web server can leave it out, as an nginx configuration without `fastcgi.conf` does. Then `getenv()` has nothing under php-fpm either, and `filter_input()` built `$_SERVER` to find nothing, in the request that compiled the routes. OPcache built it again each time it loaded a file it had compiled after that point, like `src/matcher.php`, on every request until it was reset. `make load`'s configuration was one of these, and its `Tillkite` row took 2.33 µs to load the matcher's class, in sequential requests inside php-fpm, against 1.04 µs once nothing built `$_SERVER`. So `check_document_root()` reads `$GLOBALS['_SERVER']`, which `run()` has built under `php -S` by then, and otherwise `getenv()`, and a server that passes no `DOCUMENT_ROOT` has nothing checked, as before, and nothing built.

In 7 alternating rounds of 3,000 requests to a 4-route site, with the order shuffled on every iteration, the dist file took 3.4 µs less inside the worker, 9.5 to 6.1 µs, and the client saw 3.6 µs less latency, 52.2 to 48.6 µs, while two copies of the same file differed by 0.04 to 0.08 µs. A site whose own code reads `$_SERVER` saves nothing, and loses nothing: 0.04 µs, within the noise.

OPcache records which of these superglobals existed when it finished compiling a file, not which ones it names, and builds them each time it loads that file. So a file first compiled during a request that had built `$_SERVER`, like a template that a 404 file which reads `$_SERVER['REQUEST_URI']` ran, costs the same 3.8 µs on every load until it's compiled again, even though it never names it. The saving holds for a site whose request path, from `index.php` to the templates, never names `$_SERVER`, and whose files OPcache first compiles in requests like that. So `App` has `uri()` and `method()`, which the 404 and 405 files that `new` makes, and the example site's, use instead.

### Keeping PHP's share small

On a small route set, PHP's own work costs more than `preg_match`, so the match path avoids work wherever it can:

- `Matcher` has one property. Every property is set again on every request, and one promoted property is about 43 ns cheaper than three typed ones.
- `match()` writes out the usual cases instead of calling helpers, because every function call costs time.
- Static routes and dynamic leaves are stored as ready-made match arrays. Coming from OPcache, they cost nothing to build, and copying one is about 14 ns cheaper than building it.
- Small regexes tell routes apart by the number of matches instead of a `(*MARK)`, which PHP adds to the matches as a new string.

### Why the cache rebuilds itself instead of using a build step

A separate build runs in a different environment from the web server: its own `php.ini`, environment variables and user. If routes or settings depend on anything only the web server provides, the build compiles different routes than the site uses, and nothing notices. Running the build through `index.php` also runs everything before `run()`. Keying the cache on the routes file removes the build step entirely, and the cache is always built by the web server itself.

Measured costs (the compile column comes from a rough prototype, so real numbers will be somewhat higher):

| Routes | Compile every request | Fingerprint the routes array | `stat` the routes file | Include cached compile |
|---|---|---|---|---|
| 10 | 4.8 µs | 0.9 µs | 0.8 µs | 0.05 µs |
| 50 | 23.7 µs | 3.9 µs | 0.8 µs | 0.05 µs |
| 200 | 93.7 µs | 15.9 µs | 0.8 µs | 0.05 µs |
| 1,000 | 471.5 µs | 76.6 µs | 0.8 µs | 0.05 µs |

The `stat` stays flat as routes grow, which is why the cache is keyed on the routes file's modification time rather than a fingerprint of the routes.

In the finished cache, with GitHub's routes and OPcache on, a request spends about 1.5 µs loading the routes: 0.8 µs for the `stat`, 0.5 µs building the cache file's name, which hashes the settings along with the routes file's details, and 0.2 µs including the file. The name is built from a plain string, with only the array settings JSON-encoded, because encoding all of them cost another 0.1 µs.

### Why the cache key has a hash of Tillkite's code

The key had Tillkite's version, but the compiled format can change between releases, as it did several times while groups were built. A cache that older code wrote then made every request a 500 until it was deleted. Releases were safe, because they change the version, but anyone running Tillkite from a commit wasn't.

`make dist` already runs before the tests and in CI, and CI already fails when its output differs from what's committed, so a hash of `src/` that it writes can't be forgotten, and costs one constant at request time. It changes for every change to the code, even a comment, which only costs one compile per app after an update, as a release does. Every change to `src/` changes that one line, so two branches that both change `src/` conflict there, and running `make dist` again settles it, as it does for `dist/tillkite.php`.

The hash only changes when `make dist` runs, so under `php -S`, where Tillkite itself is edited, the key also has the times of Tillkite's files. That costs a `stat` for each, seven for `src/`, which a production request doesn't pay.

Other ways considered:

- A format number, raised by hand whenever the compiled format changes. It costs nothing, but someone has to remember, and the edits before it's raised share a key.
- That number, and a test that pins a hash of what a set of routes compiles to. Forgetting fails the test, but each change takes two edits by hand, and a change the routes don't use gets through.
- The times of Tillkite's files on every request. It needs no build step, but costs production a `stat` for each file.
- Composer's record of the commit a package was installed from. It changes by itself, but does nothing for `dist/tillkite.php` or for edits that aren't committed, and costs a call on every request.
- Checking the cached data after reading it, by its shape or a format number inside it. It costs time on every request, and still misses a value whose meaning changed, as a route's group key did.

### Why the starter is part of Tillkite

A site needs a few files before it shows a page, and most of what makes a good start, like security headers, error pages that don't leak paths, and a cache directory git ignores, is the same every time. The starter makes them with one command, instead of copying each one from the README.

There are two ways in because there are two ways to get Tillkite. With Composer, a package's `bin` is the usual way to ship a command, and Composer 2.2's proxy for it says where the autoloader is, so the site requires the project's own. Without Composer, the dist file has to be the command, because it's the only file there is. So the starter is a class in `src/`, with its templates as strings, and the dist file runs it when it's the script PHP was started with. Composer's autoloader loads it only when the command runs. The dist file is about 11.6 KB larger, but under php-fpm with OPcache, loading it took the same time as before, 0.29 µs against 0.29 µs, where a second copy of the old file measured 0.25 µs. The check at its end is a comparison with `PHP_SAPI`, which is false under php-fpm.

The dist file copies itself into the site, rather than the site requiring the file that made it, so the site is complete in its own directory, and deleting the download doesn't break it.

Other ways considered:

- `composer create-project`, which copies a package as a new project. It needs a separate skeleton package, which has to be kept in step with Tillkite, and does nothing for the dist file.
- A separate installer script, downloaded and run. It's one more thing to download and trust, and the dist file can already do it.
- Templates as files in the repository. Composer could copy them, but the dist file would still need them inside it, and two copies drift.

### Why templates get $data, and not a variable for each key

A template could get a variable for each key in its data, with `extract()`, as many PHP template systems do. Tillkite doesn't use `extract()` anywhere: a variable that appears from nowhere is hard to trace back to where it was set, and a key like `tillkite` would have to be skipped, or replace the app. So a template gets the array as `$data`, as a handler gets `$params`, and reads `$data['title']`. It's a few more characters, and it's always clear where a value came from.

### Why template() returns a string

A template that printed straight to the output would cost one buffer less, about 0.1 µs, but a layout couldn't take a page's content, the most common reason to use templates. It would have to be split into a header and a footer instead. Returning a string lets a handler pass one template's output to another, or use it for something other than the page, like an email.

### Why html_attr() escapes only a few more characters

`html()` already escapes `& < > " '`, so its output can't end a quoted attribute value. An unquoted one ends at whitespace or `>`, by the HTML standard, so `html_attr()` adds whitespace, and `=` and the backtick, which old browsers treated as a value's start or its quotes. Twig, Laminas and OWASP escape every character but letters, digits and a few punctuation marks, as `&#xHH;`. That's safe too, but it takes a callback for each character, and makes plain text twice as long: a sentence's spaces each become six characters. Phalcon's attribute escaper is `htmlspecialchars()` alone, which isn't safe without quotes.

`html()` isn't enough for every attribute, and neither is `html_attr()`. The browser decodes an attribute's entities before it hands its value to the URL, JavaScript or CSS parser, so an `onclick`, `href` or `style` needs escaping for that language first: `html_attr( js() )`, `url()` or `css()`. `srcdoc` holds a page, so text in it needs `html()` for that page, then `html_attr()`. And without quotes, no escaping helps an empty value: `title= class=x` gives `title` the value `class=x`, so an attribute that can be empty needs quotes.

### Why js() escapes more than JSON needs

`json_encode()` with the `JSON_HEX_*` flags is safe in `<script>` as a value. But developers who know Twig's and Laminas's JavaScript escapers, which are for inside quotes, put quotes around it. A value like `+alert(1)+` then ends their string and runs, and so does `${alert(1)}` inside a template literal. With every character but ASCII letters and digits escaped in its strings, the text between the quotes can only be letters, digits and escapes, so code around it is a syntax error or shows the quotes, and never runs. That has to include each character outside ASCII: JavaScript reads some of them, like U+00A0 and U+3000, as spaces between words, so `in new f in`, with U+00A0 for its spaces, in quotes put around it, would be `"" in new f in ""`, which calls `f`. Escaped, it's a name that isn't valid, an error. Every escape is still valid JSON, so the output works with `JSON.parse()` too.

A Laminas-style escaper for inside quotes would need `json_encode()` anyway, for numbers, arrays and objects, so a site would have two methods for JavaScript and a rule for when to use each. It fails the other way, too: without quotes, its output is code. Escaping fewer characters doesn't work either: with `+`, `{`, `}` and `:` left as they are, `"Hi "+{valueOf:f}+""` calls `f` with no parentheses.

### Why another encoding's output is all ASCII

In Shift_JIS, GBK, Big5 and GB18030, the second byte of a character can be an ASCII byte. In Shift_JIS, 表 is `0x95 0x5C`, and `0x5C` is `\`. Escaping such text a byte at a time breaks it, and an attacker's lone first byte before an escape's `\` or `&` can join it into one character, taking the escape apart. Converting to UTF-8 to escape, then back, as Laminas does, depends on mbstring and the browser reading every character's bytes the same way. All-ASCII output depends on neither: each of these encodings reads ASCII bytes as ASCII, and nothing in the output is a byte that can start a longer character. The cost is size, about six bytes for each character outside ASCII.

### Why the compiler checks copies of its regexes

PHP keeps each process's compiled regexes in a cache, keyed by the regex string. A key from OPcache is found by its address, but a regex first run from a string built at runtime is stored under a copy, and every later lookup compares the whole regex with that copy. The compiler checks that each table's regex compiles, and uses the regexes to find hidden static routes. When it ran the final regexes, the php-fpm worker that rebuilt the route cache matched a GitHub route in 580 ns instead of 310 ns, for as long as it ran.

So the compiler runs a copy of each regex that starts with an empty comment, `(?#)`, which matches the same way but is a different string, and the request that writes the cache includes it before matching. That worker then matches as fast as any other.

### Why a route's before-file runs after the app's

At first, a route's `before` replaced the app's, so only one before-file ever ran. Now the app's runs first, then the route's, and `before_only` replaces it:

- **Mistakes fail in the safer direction.** With replacing, a route that adds a before-file quietly drops what the app's does, like security headers, the session, or loading the user, usually on admin pages, which need them most. Now the likely mistake is a route doing too much, like a webhook starting a session it doesn't need, which costs little and shows.
- **The shared scope pays off.** The app's before-file can set `$user`, and an admin before-file only has to check it.
- **It's what people expect.** Middleware in Laravel, Slim and Express works this way: the app's runs, and a route adds its own.

Other ways considered:

- Keep replacing, and have a route's before-file `require` the app's. It adds no API, but forgetting the line fails in the unsafe direction, and nothing reports it.
- A list on the route, like `'before' => [ 'before.php', 'admin-before.php' ]`. It shows everything that runs, but it's still replacing by default, and repeats the app's file on every route that adds one.
- A flag that turns the app's off, like `'app_before' => false`. Replacing would take two options, and "none" would be written differently from `'before' => false`.
- The app's before-file deciding for itself, from `$tillkite->route()`. That hides which files run inside code, instead of showing it in the routes file.

### Why groups are one level deep

A group's routes run at most three before-files: the app's, the group's and their own. So the compiler works out each route's list when it compiles, and the runner has a place for each of the three. Groups inside groups would make the list any length, and the runner would have to loop over it. It can't use a loop variable, because the files share its scope and would see it, so each file would cost a call back into `App`. One level covers the usual cases, like an admin area or an API, and allowing more later breaks nothing, because a group inside a group is a compile error until then.

Groups also cost nothing when matching, because the compiler expands them into ordinary routes first. Running a route costs about what it did before groups. Timed inside php-fpm as in [Under load](#under-load), on the GitHub routes' last route, 3,000 requests to each of two copies of each version put a hit at 9.17 µs instead of 9.12, one tick of the timer, and a miss didn't change.

The route cache stores the before-file paths once for every route that runs only the app's, and separately only for the routes that run something else, or are in a group. Storing every route's paths, its handler's too, made a hit 0.08 µs faster than before groups, but made the GitHub routes' cache file 37% larger, 833 KB instead of 610.

A group's error files don't slow a hit either, because `Matcher` looks for the group a path is under only after a miss, and only when there are groups. Timed the same way, with no group error files, as in the GitHub routes, a hit's `run()` took 8.21 µs before and after, and a miss's took 0.04 and 0.09 µs longer in the two pairs, one and two ticks of the timer. The first version looked in `App` instead, which checked the status of every match. Its hits measured 0 to 0.12 µs slower across runs, close to the noise, but in `Matcher` a hit runs no new code.

`group()` costs a hit in a group one more property set. It costs a miss in an app with groups the regex that finds its group, which used to run only when a group had before-files, error files or parameters of its own: about 0.3 µs for `preg_match()`, and 0.3 µs for keeping the group. Timed the same way, with the GitHub routes all in one group under `/v3`, a hit's `run()` took 7.46 µs instead of 7.38, and a miss's took 7.54 µs instead of 6.96, in both pairs. Without groups, both stayed within 0.08 µs. Finding a miss's group only when `group()` asks would save that, but would mean keeping the path and the compiled routes for later.

Other ways considered:

- A group written by position, like `[ '/admin', [ 'before' => 'admin-before.php' ], [ ... ] ]`. It's shorter, but a group has more parts than a route, and the keys say what each one is.
- A method that builds groups, like FastRoute's `addGroup()`. The routes file would need an object to call, instead of returning a list.

### Why misses run the before-files

At first, before-files ran only for a route that matched, as middleware does in routers that attach it to routes, like Laravel's route groups. That left a gap in a login check. A visitor it turned away got a 405 with an `Allow` header for a `GET` of a route that takes only `POST`, and a 308 for a route with the other trailing slash, but a 404 for a path that doesn't exist, so they could find out which paths exist. Express's `app.use( '/admin', ... )` runs for every path under `/admin`, matched or not, and Tillkite now does the same:

- **One rule.** A before-file runs for every request it covers. The app's covers every path, and a group's covers its prefix.
- **The headers come along.** The app's security headers go out with the 404 page, and an API group's JSON headers with its error pages, so its error files don't repeat them.
- **No switch.** A login check that covers only the routes that match is the surprise, so there's no option to turn this off. `'before' => false` on a group still runs nothing under its prefix.

Timed inside php-fpm as in [Under load](#under-load), on the GitHub routes, with 3,000 requests to each of two copies of each version, and no before-file, a miss's `run()` took 7.67 and 7.71 µs instead of 7.58, and a hit's took 0.04 to 0.08 µs longer, although a hit runs no new code. With an app before-file that sends one header, a miss took 9.25 µs instead of 7.62, where the same file adds 0.4 µs to a hit. To run it, a miss starts a buffer, times the step and throws the output away. A hit does those for its handler anyway, and a miss without a before-file never does.

Other ways considered:

- Running a group's before-files for the misses under its prefix, but never the app's. It changed nothing released, since groups weren't yet, but `before.php` would run for `/admin/nope` and not for `/nope`.
- Answering a 405 as a 404 under a group. It hides the `Allow` header, but not the 308, and visitors who are signed in lose their 405s.
- A catch-all route at the end of a group, whose handler calls `error( 404 )`. It works without any change to Tillkite, but it catches what would have been a 405 or a 308 too.

### Why error() waits for the file to return

Tillkite throws no exceptions, so `error()` can't stop the file that calls it. The question was what happens when that file goes on, because someone left off the `return`:

- **Running the error file at once, inside `error()`.** It's the simplest, but a forgotten `return` adds the rest of the page after the error page, and a before-file's login check still lets the handler run.
- **Recording the code, and acting when the file returns.** That's what it does. A forgotten `return` only wastes the rest of that file's work. The handler never runs after a before-file that called it, which matters most for login checks. And it throws away the whole page, not just what came before the call.

It costs a check before the handler, and one more call into `App` before a route's own before-file. Timed inside php-fpm as in [Under load](#under-load), on a route without before-files, three runs of 4,000 to 6,000 requests each put it at 0.05 µs a request on average, less than the runs differed from each other.

Other ways considered:

- An exception, caught by Tillkite. Tillkite doesn't use them, and a handler's own `catch ( \Throwable )` would swallow it.
- `exit`. It ends the request before Tillkite can throw away the buffer and run the error file, so it would all happen in the shutdown function, and code after `run()` in `index.php` would never run.
- Including the error file in the handler's scope, as the README showed before. That page would see the handler's variables, and look different depending on where it was shown from.

### Why buffering is on by default

Headers go out before the body, and PHP's default 4 KB output buffer means most pages send headers while the handler is still running. Buffering lets handlers set headers at any time, makes 500 pages clean, and makes the timing header exact. Streaming routes and large downloads turn it off per route, or the whole app turns it off with `buffer`.

### Why Tillkite doesn't throw exceptions

Exceptions and `try`/`catch` are kept to the absolute minimum. Tillkite catches nothing. Its one `try` is the `try`/`finally` in `template()`, which only cleans up after a template that throws, and lets the exception go on. Configuration problems are collected and reported by `run()`, internal failures are checked through return values, `set_exception_handler()` runs the 500 file for exceptions thrown by the app's code or by PHP, and a shutdown function sends a one-line 500 after a fatal error. Tillkite defines no exception classes, so none become part of the public API.
